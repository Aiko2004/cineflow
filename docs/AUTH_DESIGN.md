# auth-service — проект первого шага

Порт 8084. Postgres (аккаунты, refresh-токены) + Redis (OTP-коды, rate limit).

Объём: только OTP по email. Telegram, OAuth и Keycloak — следующими шагами.

---

## 1. Данные в Postgres

### `users`

| Колонка | Тип | Комментарий |
|---|---|---|
| `id` | UUID | UUIDv7, PK |
| `email` | VARCHAR(320) | UNIQUE, NOT NULL |

| `phone` | VARCHAR(20) | UNIQUE, nullable — смена телефона появится позже |
| `role` | VARCHAR(32) | NOT NULL, пока всегда `USER` |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL |

**Колонки с паролем нет вообще** — вход только по одноразовому коду. Нечего утекать, нечего перебирать, не нужна политика сложности и сброс.

**Почему UUID, а не `Long`.** Контракт фронтенда требует `string`. Плюс последовательные идентификаторы утекают информацию: по `id=1043` видно, сколько всего пользователей, и можно перебирать чужие. Для сущностей вроде фильмов это неважно, для аккаунтов — важно. Сервис новый, миграции нет, платить за это не приходится.

**`email` ограничен 320 символами** — максимум по RFC (64 на локальную часть + @ + 255 на домен).

### `refresh_tokens`

| Колонка | Тип | Комментарий |
|---|---|---|
| `id` | UUID | UUIDv7, PK |
| `user_id` | UUID | FK → users, **индексировать** |
| `token_hash` | VARCHAR(64) | SHA-256 от токена, UNIQUE |
| `family_id` | UUID | UUIDv7, общий для цепочки ротаций, индексировать |
| `expires_at` | TIMESTAMPTZ | NOT NULL |
| `revoked_at` | TIMESTAMPTZ | nullable |
| `created_at` | TIMESTAMPTZ | NOT NULL |

**Хранится хеш, а не сам токен** — по той же причине, по которой не хранят пароли в открытом виде. Утечка таблицы не даёт возможности войти.

**`family_id` — для обнаружения кражи.** Разберём ниже, в разделе про ротацию.

### Про версию UUID

Везде **UUIDv7**, генерируется приложением через `com.github.f4b6a3:uuid-creator` — так же, как уже сделано в screening-service.

Причина: первые 48 бит v7 — метка времени, поэтому новые значения монотонно растут и вставки ложатся в конец B-дерева, как у автоинкремента. Случайные v4 раскидывают вставки по всему индексу: каждая попадает в холодную страницу, дерево фрагментируется, страницы расщепляются. Для `refresh_tokens` это критично — таблица с самой высокой частотой вставок в сервисе (строка создаётся и при входе, и при каждой ротации).

Оговорка по `family_id`: значение создаётся один раз при входе и переиспользуется при всех последующих ротациях, поэтому сегодня в индекс может вставляться метка месячной давности. Выигрыш от упорядоченности здесь частичный, но не отрицательный.

**Обратная сторона v7:** метка времени читается из идентификатора. По `users.id` видно, когда создан аккаунт, и можно сравнить двух пользователей — кто раньше. Угадать чужой идентификатор по-прежнему нельзя (это и было главной причиной ухода от `Long`), но полной непрозрачности нет. Для времени регистрации это приемлемо; для сущностей, где сам момент создания чувствителен, выбор был бы другим.

**Колонки объявлять типом `UUID`, не `VARCHAR(36)`.** Нативный тип — 16 байт и сравнение двух 64-битных слов; строка — 36+ байт и посимвольное сравнение, плюс вдвое более толстый индекс. Именно отсюда обычно растёт мнение, что «UUID тормозят».

## 2. Данные в Redis

```
otp:{email}                 Hash { code_hash, attempts }   TTL 5 мин
otp:rate:email:{email}      счётчик                        TTL 15 мин
otp:rate:ip:{ip}            счётчик                        TTL 15 мин
```

**Почему Redis, а не Postgres.** Код живёт пять минут и потом не нужен никому. В Postgres пришлось бы заводить таблицу и фоновую задачу, вычищающую протухшие записи. В Redis ключ истекает сам — та же логика, по которой там будут удержания мест при бронировании.

**Код хранится хешем.** Он короткий и живёт недолго, так что выигрыш скромный, но принцип «секреты не лежат в открытом виде» стоит соблюдать везде, а не выборочно.

**Два независимых лимита.** По email — чтобы не заваливать письмами одного человека. По IP — потому что иначе атакующий просто перебирает разные адреса с одной машины, и лимит по email его не останавливает.

## 3. Payload токена

```json
{
  "iss": "https://auth.cineflow.local",
  "sub": "0199c4f2-...",
  "aud": "cineflow-api",
  "email": "user@example.com",
  "roles": ["ROLE_USER"],
  "jti": "0199c4f3-...",
  "iat": 1758553200,
  "exp": 1758554100
}
```

**Payload читается кем угодно** — base64 это кодирование, а не шифрование. Поэтому здесь только то, что не жалко показать: идентификатор, email, роли. Ни телефона, ни имени, ни чего-либо чувствительного.

**`iss` — ключевое поле для гибридной схемы.** Именно по нему Gateway отличит токен, выданный нами, от токена Keycloak, когда тот появится для админских ролей.

**`jti`** — уникальный идентификатор токена. Сейчас не используется, но без него нельзя будет сделать чёрный список, если он однажды понадобится.

**Время жизни:** access — 15 минут, refresh — 30 дней.

## 4. Ключи и их распространение

Подпись RS256. Приватный ключ только у auth-service, публичный раздаётся через `GET /.well-known/jwks.json`:

```json
{ "keys": [ { "kty": "RSA", "kid": "...", "use": "sig", "alg": "RS256", "n": "...", "e": "AQAB" } ] }
```

Каждый защищаемый сервис указывает у себя `spring.security.oauth2.resourceserver.jwt.jwk-set-uri` и дальше всё делает Spring: забирает ключи, кеширует, при встрече неизвестного `kid` перезапрашивает.

**Почему не HS256 с общим секретом.** При симметричной подписи любой сервис, умеющий проверять токен, умеет его и подделать. Скомпрометировали screening-service — злоумышленник выписывает себе токен администратора. При RS256 подделать может только владелец приватного ключа.

**`kid` в заголовке токена** позволяет менять ключи без простоя: выкатываем новый ключ, какое-то время отдаём в JWKS оба, старые токены продолжают проверяться старым.

## 5. Эндпоинты

```
POST /auth/otp/send     { email, type }        → 202  { expiresIn }
POST /auth/otp/verify   { email, code, type }  → 200  { accessToken, refreshToken, expiresIn }
POST /auth/refresh      { refreshToken }       → 200  новая пара
POST /auth/logout       { refreshToken }       → 204
GET  /.well-known/jwks.json                    → публичные ключи
```

Пути совпадают с контрактом реального фронтенда (`frontend/src/api/requests/auth.ts` в референс-проекте), включая поле `type` в запросах OTP — оно понадобится, когда добавится вход по телефону.

## 6. Поток входа

```
1. Клиент → POST /auth/otp/send { email }
   - проверить лимиты по email и IP
   - сгенерировать 6-значный код
   - записать в Redis: otp:{email} = { hash(code), attempts: 0 }, TTL 5 мин
   - залогировать код (позже — отправка через Notification Service)
   - ответить 202 всегда, даже если email неизвестен

2. Клиент → POST /auth/otp/verify { email, code }
   - достать из Redis, нет → 400
   - attempts >= 5 → удалить ключ, 429
   - hash не совпал → attempts++, 400
   - совпал → удалить ключ (одноразовость)
   - найти users по email, нет → создать (регистрация неявная)
   - выпустить access + refresh (новый family_id)
```

**Почему `/otp/send` отвечает 202 всегда.** Если отвечать по-разному для существующего и несуществующего адреса, эндпоинт превращается в инструмент проверки, зарегистрирован ли человек в сервисе. Это называется user enumeration и считается утечкой.

**Почему ключ удаляется при исчерпании попыток**, а не просто блокируется счётчик: иначе атакующий запрашивает новый код и продолжает перебор с тем же результатом.

## 7. Поток обновления и обнаружение кражи

```
Клиент → POST /auth/refresh { refreshToken }
  - найти по hash(refreshToken)
  - не найден / истёк           → 401
  - revoked_at не пуст          → ТРЕВОГА: отозвать всю family, 401
  - иначе: пометить revoked_at, выпустить новую пару с тем же family_id
```

Это **ротация с обнаружением повторного использования**, и ради неё в таблице есть `family_id`.

Логика такая. Каждый refresh одноразовый: использовал — он помечен отозванным, взамен выдан новый. Если кто-то предъявляет уже отозванный токен, возможны два объяснения, и оба плохие: либо токен украли и вор пришёл после законного владельца, либо украли и вор пришёл первым, а теперь пришёл владелец. Различить их невозможно, поэтому отзывается вся цепочка — и вор, и владелец оказываются разлогинены. Владелец просто войдёт заново по коду, вор не сможет.

Без `family_id` пришлось бы отзывать вообще все сессии пользователя, включая телефон и рабочий компьютер, к которым инцидент отношения не имеет.

## 8. Что защищается на этом шаге

**api-gateway** — проверяет токен, отдаёт 401 без него. Явный список публичных маршрутов: каталог фильмов, расписание, сеансы, сам `/auth/**`.

**movie-service** — образец защищённого ресурсного сервиса: чтение открыто, `POST /movies` требует аутентификации. По этому образцу потом закрываются остальные.

Проверка идёт и на Gateway, и в самом сервисе. Полагаться только на периметр — это «твёрдая скорлупа при мягкой сердцевине»: любой, кто оказался внутри сети, ходит куда хочет. Проверка в сервисе стоит трёх строк конфига.

## 9. Открытые вопросы на потом

- Ключ для локальной разработки генерируется при старте. Для прода нужен внешний источник — переменная окружения или секрет-менеджер, иначе после каждого перезапуска все выданные токены становятся невалидными, а при нескольких экземплярах сервиса они ещё и подпишут разными ключами.
- Чистка протухших `refresh_tokens` — таблица растёт, нужен периодический `DELETE` по `expires_at`.
- Keycloak для admin/manager — отдельным шагом, вместе с разделением маршрутов `/admin/**`.

## 10. Доставка OTP — план на три шага

Отправка вынесена за интерфейс `OtpSender`, потому что реализация заведомо сменится трижды. Место вызова в `OtpService` при этом не меняется.

```java
interface OtpSender { void send(String email, String code); }
```

**Шаг 1 (сейчас).** `LoggingOtpSender` — код в лог.

**Шаг 2.** `SmtpOtpSender` через Spring Mail. Локально — **Mailpit** в docker-compose (поддельный SMTP с веб-интерфейсом на 8025): приложение отправляет по-настоящему, письма перехватываются и видны целиком, вместе с отрендеренным шаблоном. Снаружи — **Brevo** (300 писем/день, бессрочно, SMTP и API).

**Шаг 3 (Фаза 6).** `EventOtpSender` — публикация события в Kafka, доставка через Notification Service с повторами и DLQ.

### Почему не отправлять синхронно из обработчика

SMTP-рукопожатие плюс задержка провайдера — сотни миллисекунд удержания запроса. Хуже то, что вход в систему становится зависим от доступности почты: провайдер лёг — `/otp/send` падает. `@Async` снимает задержку, но письмо теряется при перезапуске процесса и повторить его нечем. Очередь решает и то, и другое: auth отвечает сразу, доставка переживает перезапуск и ретраится.

### Что понадобится до шага 2

Домен с настроенными SPF, DKIM и DMARC — без них письма уходят в спам, и кодом это не лечится. Домен есть бесплатно в GitHub Student Pack (Namecheap, на год).
