# booking-service — проект

Порт 8085. Postgres (брони, занятые места) + Redis (мягкие удержания при выборе мест).

Объём первого шага: бронирование **без оплаты**. Подтверждение — заглушкой. Payment и полная сага — Фаза 4, но модель данных и состояния закладываются под них сразу.

---

## 1. Задача

Продать конкретное место ровно один раз. Всё остальное в сервисе — обслуживание этого инварианта.

Сложность в том, что между «пользователь выбрал место» и «бронь подтверждена» проходит время: он смотрит на схему зала, потом вводит данные карты. Всё это время место должно быть недоступно другим, хотя подтверждённой брони ещё нет.

---

## 2. Данные

### `bookings`

| Колонка | Тип | Комментарий |
|---|---|---|
| `id` | UUID | UUIDv7, PK |
| `user_id` | UUID | из claim `sub` токена, индексировать |
| `screening_id` | UUID | идентификатор сеанса из screening-service |
| `status` | VARCHAR(16) | PENDING / CONFIRMED / CANCELLED / EXPIRED |
| `total_price` | NUMERIC(10,2) | сумма по местам на момент брони |
| `hold_expires_at` | TIMESTAMPTZ | до какого момента бронь держит места |
| `qr_code` | VARCHAR(255) | заполняется при подтверждении, nullable |
| `screening_date` | DATE | денормализация под контракт фронтенда |
| `screening_time` | TIME | то же |
| `movie_*`, `theater_*`, `hall_*` | — | снапшоты: фильм (id, title, slug, banner), кинотеатр (id, name, address), зал (id, name) |
| `idempotency_key` | VARCHAR(64) | UNIQUE вместе с `user_id`, nullable |
| `created_at` / `updated_at` | TIMESTAMPTZ | |

Снапшоты — по той же причине, что в screening-service: `GET /bookings/@me` должен отдавать название фильма и адрес кинотеатра без обращения к трём чужим сервисам. И цена в брони обязана быть зафиксирована на момент покупки: если завтра сеанс подорожает, старая бронь не должна измениться.

### `booking_seats`

| Колонка | Тип | Комментарий |
|---|---|---|
| `id` | UUID | UUIDv7, PK |
| `booking_id` | UUID | FK → bookings, **индексировать** |
| `screening_id` | UUID | денормализация, нужна для индекса ниже |
| `seat_id` | BIGINT | из theater-service (там `Long`) |
| `row_number`, `seat_number` | INT | снапшот места |
| `seat_type` | VARCHAR(32) | снапшот |
| `price` | NUMERIC(10,2) | цена именно этого места |
| `released_at` | TIMESTAMPTZ | nullable; заполнен — место освобождено |

### Ключевой элемент — частичный уникальный индекс

```sql
CREATE UNIQUE INDEX uk_seat_taken
    ON booking_seats (screening_id, seat_id)
    WHERE released_at IS NULL;
```

Это и есть гарантия «одно место — один раз». Обычный `UNIQUE (screening_id, seat_id)` не подошёл бы: после отмены брони место должно снова продаваться, а уникальность по всей истории это запрещает. Условие `WHERE released_at IS NULL` ограничивает уникальность только **активными** записями — история отменённых броней сохраняется, но на доступность места не влияет.

Отсюда и `screening_id` дублируется в этой таблице: оба столбца индекса обязаны лежать в одной таблице, а `screening_id` живёт на уровне брони.

## 3. Состояния и переходы

```
                   POST /bookings
                         │
                         ▼
                     PENDING ──────── confirm ────────▶ CONFIRMED
                      │   │                                  │
               cancel │   │ hold_expires_at прошёл           │ cancel
                      │   │ (фоновая задача)                 │ (возврат — Фаза 4)
                      ▼   ▼                                  ▼
                 CANCELLED  EXPIRED                      CANCELLED
```

Инварианты:

- Места удерживают только `PENDING` и `CONFIRMED` — у их записей в `booking_seats` поле `released_at` пустое.
- `CANCELLED` и `EXPIRED` — терминальные. Обратных переходов нет: из `CONFIRMED` нельзя вернуться в `PENDING`.
- Переход выполняется **условным `UPDATE`**, а не чтением с последующей записью:
  ```sql
  UPDATE bookings SET status = 'CONFIRMED' WHERE id = :id AND status = 'PENDING'
  ```
  Ноль затронутых строк — значит статус уже изменился (кто-то отменил, истекло, или это повторный запрос). Это тот же приём, что в ротации refresh-токенов: проверять и менять одной атомарной операцией, иначе два параллельных запроса оба пройдут проверку.

Переходы принадлежат сущности `Booking`, а не сервисному слою. До сих пор наши сущности были анемичными — набор геттеров без поведения. Здесь это перестаёт работать: правило «из CONFIRMED нельзя в PENDING» должно жить в одном месте, а не повторяться в каждом вызывающем методе.

## 4. Три слоя защиты от двойной продажи

Здесь важно честно разделить, что обеспечивает **корректность**, а что — **удобство**.

### Слой корректности: частичный уникальный индекс

Единственная настоящая гарантия. Даже если Redis лежит, перезапустился или потерял ключи, база не даст вставить вторую активную запись на то же место. Всё остальное — оптимизация вокруг этого.

### Слой удобства: Redis-удержание на этапе выбора мест

Продуктовый вопрос: в какой момент место становится занятым — когда пользователь **кликнул** его на схеме зала, или когда нажал «забронировать»?

Если только на «забронировать», то пока десять человек выбирают места, все видят их свободными, и девять получат отказ в последний момент. Плохой опыт на премьере, где все целятся в одни и те же кресла.

Если на клик — нужно удержание **до** создания брони. Заводить запись в БД на каждый клик по схеме зала не хочется: пользователь потыкал пять мест, передумал, ушёл — в таблице мусор. Вот здесь Redis на месте: ключ с коротким TTL, без записи в БД, истекает сам.

```
Клик по месту:  SET seat:{screeningId}:{seatId} {userId} NX EX 120
                NX не сработал → место кто-то держит → 409
Снятие выбора:  DEL, но только если значение == свой userId
```

Проверка владельца при удалении обязательна: иначе запрос одного пользователя снимет удержание другого, чей TTL как раз истекал.

### Слой уборки: истечение удержания брони

`PENDING` с прошедшим `hold_expires_at` — это брошенная бронь: человек начал оформление и не закончил. Фоновая задача переводит её в `EXPIRED` и ставит `released_at` её местам, освобождая индекс.

Важно: проверка доступности места смотрит не только на существование активной записи, но и на `hold_expires_at`. Иначе место оставалось бы занятым до следующего запуска уборщика.

### Почему именно так, а не иначе

Технически можно обойтись **только** базой: создавать `PENDING`-бронь сразу при выборе мест и полагаться на индекс. Корректность при этом не страдает вообще. Redis добавляет две вещи: отсутствие записей в БД на этапе «пользователь ещё думает», и дешёвый отказ без попытки вставки с откатом транзакции.

То есть Redis здесь — не гарантия, а оптимизация на горячем пути плюс продуктовое решение про момент удержания. Это стоит понимать и уметь проговорить: если на собеседовании сказать «места защищены Redis-локом», следующий вопрос будет «а если Redis перезапустится?» — и ответ должен быть «ничего, корректность на индексе».

## 5. Внешние вызовы

**Screening Service — gRPC.** `GetScreening(screeningId)` отдаёт: существует ли сеанс, `startAt`/`endAt`, типы мест с ценами, снапшоты фильма/зала/кинотеатра. Один вызов покрывает и валидацию, и данные для денормализации.

Это та самая связка, которую мы пометили как осознанную практику с protobuf: REST справился бы, но это самый частый внутренний вызов в системе. Контракт — в модуле `contracts`, `.proto`.

**Theater Service — REST/Feign.** Нужно проверить, что запрошенные `seatId` действительно существуют в этом зале, и получить их ряд/номер/тип для снапшота и расчёта цены. По конвенции — обычный Feign, без gRPC.

Оба вызова — под circuit breaker, bulkhead и retry, по образцу `ScreeningEnrichmentService`. Вызовы делаются **до** открытия транзакции: держать соединение с БД во время сетевых запросов нельзя (разбирали на транзакциях).

### Аутентификация gRPC-порта 9083 — осознанное решение

gRPC-порт screening (9083) **не аутентифицирован** на уровне приложения (`InsecureServerCredentials`, без mTLS). Это допустимо, потому что порт — **строго внутренний** и это обеспечено технически, а не подразумевается:

- он **не проксируется** через api-gateway (gateway работает только с HTTP; JWT проверяется на HTTP-эндпоинтах, gRPC мимо периметра не выходит);
- он **не публикуется** в `docker-compose` (сервисы там вообще не контейнеризованы; когда будут — порт 9083 просто не получит `ports:`-маппинг и останется во внутренней сети);
- в текущем dev-режиме (сервисы как host-JVM) gRPC-сервер по умолчанию биндится на **loopback** (`127.0.0.1`, `grpc.server.host`) — недоступен из LAN, его видит только co-located `booking-service`. То есть «внутренний» — проверяемый факт, а не допущение.

Альтернатива — **mTLS** (взаимная TLS-аутентификация сервисов). Для пет-проекта избыточно: она защищает от злоумышленника, УЖЕ находящегося во внутренней сети, а такой модели угроз здесь нет. Если вызов однажды пересечёт границу доверия (другой кластер, публичная сеть) — переключить `InsecureServerCredentials` → `TlsServerCredentials`; шов в `screening-service` `GrpcServer`.

## 6. Идемпотентность

`POST /bookings` принимает заголовок `Idempotency-Key`. Ключ хранится в `bookings` с `UNIQUE (user_id, idempotency_key)`.

Зачем: клиент отправил запрос, получил таймаут, повторил — без ключа получилось бы две брони на те же места, причём вторая упала бы на уникальном индексе мест и пользователь увидел бы ошибку, хотя первая бронь создалась успешно. С ключом повтор возвращает **ту же** бронь.

Для операций с деньгами это обязательная вещь, а не украшение. Здесь оплаты пока нет, но закладываем сразу — в Фазе 4 переделывать было бы дороже.

## 7. Эндпоинты

```
POST   /bookings/seats/hold      { screeningId, seatIds[] }  → 200 { holdExpiresAt }
DELETE /bookings/seats/hold      { screeningId, seatIds[] }  → 204
POST   /bookings                 { screeningId, seatIds[] }  → 201 { booking }
                                 заголовок Idempotency-Key
POST   /bookings/{id}/confirm                                → 200 { booking + qrCode }
POST   /bookings/{id}/cancel                                 → 200 { booking }
GET    /bookings/@me                                         → Slice<BookingResponse>
GET    /bookings/{id}                                        → 200 { booking }
```

`user_id` берётся **только** из токена, никогда из тела запроса — иначе любой сможет создать бронь от чужого имени. `GET /bookings/{id}` проверяет владельца: чужая бронь — 404, а не 403 (403 подтверждает, что бронь существует).

Форма `BookingResponse` — по контракту фронтенда: `{ id, screeningDate, screeningTime, movie{}, theater{}, hall{}, seats[], qrCode }`.

В Фазе 4 добавится `POST /payment/init`, который по контракту создаёт бронь и платёж вместе.

## 8. QR-код

Генерируется при подтверждении. Содержимое **не должно быть угадываемым**: если закодировать только `bookingId`, кто угодно подберёт чужой и пройдёт по нему в зал. Нужен либо случайный токен, хранящийся с бронью, либо подпись — HMAC от `bookingId` секретом сервиса, проверяемая на входе в кинотеатр.

Проще случайный токен: 256 бит из `SecureRandom`, никакой криптографии при проверке, просто поиск по индексу.

## 9. Задел под сагу (Фаза 4)

Модель уже готова к этому: `PENDING` + `hold_expires_at` — это и есть состояние «ждём оплату».

Один сценарий стоит продумать заранее, потому что он про деньги. Удержание истекло, место переоткрылось и продалось другому, **а платёж первого пользователя в этот момент успешно завершился**. Деньги взяли за место, которое отдать нельзя.

Защита двухслойная: окно оплаты заведомо короче `hold_expires_at`, и при получении подтверждения платежа проверяется, что бронь всё ещё `PENDING` и удержание не истекло. Если нет — автоматический возврат, а не подтверждение.

## 10. Открытые вопросы

- Частота уборщика брошенных `PENDING`. Слишком редко — места простаивают; слишком часто — лишняя нагрузка. Начать с минуты.
- Длительность удержаний: 2 минуты на выбор места (Redis), 10 минут на оформление брони. Числа взяты из здравого смысла, проверять некому — пользователей нет.
- Лимит мест в одной брони: без ограничения один запрос может заблокировать весь зал. Начать с 10.
- Кто отменяет бронь после начала сеанса — и можно ли вообще. Пока считаем, что `CONFIRMED` отменяется до `startAt`.
